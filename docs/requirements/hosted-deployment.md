# ホスト運用の要件

devpulse をチームで共有する 1 インスタンスとしてホストするための要件を定める。メトリクスの定義・算出方法・チャートの見た目は対象ではない。
定めるのは「ホストされた devpulse が誰に何を許し、データをどこにどう保つか」である。

## 用語

| 語 | 意味 |
|---|---|
| インスタンス | ホストされた devpulse のプロセスと、それが使う 1 つの PostgreSQL データベース |
| ワークスペース | インスタンスが保持するリポジトリ・メトリクス・トークンの全体。インスタンスに 1 つだけ存在する |
| 収集 | GitHub API からリポジトリのデータを取得し、データベースへ書き込む処理 |
| 収集ジョブ | 1 回の収集の実行単位。識別子を持ち、進捗と結果を報告する |
| 既定トークン | トークンが明示されないときに使われる GitHub トークン |

## 前提

インスタンスは常駐プロセスとして動き、収集ジョブはそのプロセス内で走る。1 つの PostgreSQL データベースを使い、ほかの永続ストレージを
必要としない。再起動でコンテナの中身が失われても、データベースにあるものはすべて残る。ホスト先は問わず、これらを満たす環境で動作する。

## 認証と認可

### UC-01 ログインする

インスタンスは GitHub アカウントで利用者を認証する。認証に成功し、かつ許可リストに合致する利用者だけが
ワークスペースに入れる。許可リストは GitHub organization 名か GitHub login の列挙で与え、両方が与えられた
ときはどちらかを満たせば通る。

- セッションは署名付き Cookie に保持する。インスタンスはセッションをデータベースに保存しない
- セッションの有効期限は 7 日である。期限切れの利用者は再度ログインする
- 未ログインの要求は、画面であればログイン画面へ遷移し、API であれば `401` を返す
- 許可リストに合致しない利用者は `403` を受け取り、ワークスペースの内容を一切見られない
- 許可リストがどちらも設定されていないとき、インスタンスは起動を拒否する
- ログインした利用者は全員同じ権限を持ち、UC-02 から UC-12 のすべてを実行できる。利用者ごとの権限差・
  データの出し分けは存在しない

### UC-02 ログアウトする

利用者はログアウトでき、その後の要求は未ログインとして扱われる。ログアウトが終わらせるのはそのブラウザの
セッションだけである。インスタンスは発行済みの Cookie を他所で失効させる手段を持たず、漏れた Cookie は
有効期限まで通る。

## ワークスペース

ワークスペースはインスタンスに 1 つだけ存在し、ログインした利用者全員が同じ内容を見る。リポジトリ・
収集済みデータ・GitHub トークンのいずれも、利用者に紐づかない。

### UC-03 リポジトリを一覧する

利用者はワークスペースに追加済みのリポジトリを一覧できる。各リポジトリについて、表示名と最終収集日時と、
収集に使うトークンが分かる。一度も収集していないリポジトリは、最終収集日時が空のまま一覧に現れる。

### UC-04 リポジトリをワークスペースに追加する

利用者は GitHub 上のリポジトリを検索し、ワークスペースに追加する。検索範囲は、トークンを指定した場合は
そのトークンで到達できる範囲、指定しない場合は登録済みのすべてのトークンで到達できる範囲の和集合である。
トークンが 1 つも無い場合、検索は失敗し、その旨が利用者に伝わる。

### UC-11 リポジトリをワークスペースから削除する

利用者はリポジトリを削除できる。削除すると、そのリポジトリについて収集したデータはすべて失われる。削除は
取り消せない。ほかのリポジトリのデータは影響を受けない。

## 収集

### UC-05 リポジトリのデータを収集する

利用者は収集を開始する。収集は次の 3 つの態様を持つ。初回の収集は差分の起点が無い場合にあたり、結果として
すべてを取得する。

| 態様 | 取得範囲 |
|---|---|
| 差分（既定） | 前回の収集以降に更新されたもの |
| 起点を指定 | 指定した時点以降に更新されたもの。過去に遡って取り直すために使う |
| 全再取得 | 起点を無視し、すべてを取り直す |

- 収集は、明示されたトークン、既定トークン、環境変数のトークンの順で最初に見つかったものを使う
- 収集は開始要求に対して直ちにジョブ識別子を返し、処理はその後も続く。完了後、そのリポジトリの最終収集日時が更新される
- GitHub が Projects の読み取りを許さない場合でも収集は成功する。Priority と Size は、すでに保存されている
  値と、GitHub のネイティブ issue フィールドから読めた値が残り、Projects 由来の値だけが更新されない。
  読めなかった理由はリポジトリに記録され、画面で確認できる
- トークンが GitHub に拒否された場合、収集は失敗として終わり、理由が利用者に伝わる
- 同じリポジトリに対する収集は、インスタンスが何台動いていても同時に 1 つまで走る。実行中に新たな収集を
  求められた場合、インスタンスは実行中のジョブを返し、二重に走らせない

### UC-06 収集の進捗を見る

利用者はジョブ識別子で収集の状態（待機中・実行中・成功・失敗）と進捗を問い合わせられる。

- ジョブの状態はインスタンスの外に残る。あるインスタンスが開始したジョブの状態を、別のインスタンスも、
  再起動後の同じインスタンスも返せる
- インスタンスが再起動した場合、実行中だったジョブは失敗として記録され、利用者は再実行できる
- 存在しないジョブ識別子への問い合わせは `404` を返す

### 上限と限界

- 1 回の収集が GitHub から読むページ数には上限がある。上限に達した収集は成功として終わり、取得できた範囲
  までを保存する。上限に達したことは収集の結果に記録され、利用者に伝わる
- リポジトリ検索が 1 トークンあたりに返す件数には上限がある。上限を超える範囲は検索語で絞る
- GitHub のレート制限に達した収集は失敗として終わる。再試行してよい時刻が利用者に伝わる
- 上記のいずれもデータベースの内容を壊さない。途中まで保存されたデータはそのまま有効である

## 閲覧と書き戻し

UC-07・UC-08・UC-10 はデータベースを読むだけで、GitHub API を呼ばない。収集が一度も行われていない
リポジトリでは、いずれも空の結果を返し、エラーにはならない。

- **UC-07 メトリクスを見る** — DORA メトリクスと個人別の集計を閲覧する。期間の切り替えと日付での絞り込みが
  でき、複数のリポジトリを並べて比較できる
- **UC-08 Issue の依存関係を見る** — 依存関係をグラフとテーブルで閲覧する。絞り込み条件は URL に保持され、
  同じ URL を開いた利用者は同じ表示を得る
- **UC-10 データをエクスポートする** — 収集済みのデータを JSON と CSV で書き出す

### UC-09 Issue の依存関係・フィールドを編集し、GitHub に書き戻す

利用者は Issue の依存関係と、Priority・Size・担当者を編集できる。編集は GitHub に書き戻され、成功した場合に
かぎりインスタンス側のデータへ反映される。

- 書き戻しに使うトークンは、そのリポジトリに紐づくトークンである。紐づくトークンが無い場合は既定トークンを使う
- トークンに書き込み権限が無い場合、編集は拒否され、権限不足であることが利用者に伝わる
- GitHub が編集を受け付けなかった場合、インスタンス側のデータは変更されない

## 秘密情報

- GitHub トークンは暗号化してデータベースに保存する。復号鍵は環境変数で与える
- 復号鍵が設定されていないとき、インスタンスは起動を拒否する。鍵を自動生成しない
- 復号鍵が変わると保存済みのトークンはすべて復号できなくなる。一覧は表示できるが復号には失敗し、利用者は登録し直す
- トークンの平文は、登録時を除いて画面にも API 応答にも現れない。現れるのは末尾 4 文字だけである
- 利用者から渡された値を、データベースへの問い合わせに文字列として埋め込まない
- GitHub への到達は、トークンの検証を含めてすべて設定されたベース URL を経由する

### UC-12 GitHub トークンを登録・検証・既定化・削除する

利用者はトークンを登録・削除し、どれを既定にするかを選べる。登録時、インスタンスは GitHub に問い合わせて
トークンが有効かを確かめ、無効なものを保存しない。最初に登録されたトークンが既定になる。既定のトークンを
削除した場合、残っているうち最も古く登録されたものが既定になる。

トークン管理 UI を禁じる設定のとき、画面からのトークンの追加・削除・変更は `403` で拒否される。一覧の表示、
登録済みトークンの検証、環境変数で与えたトークンの使用は妨げられない。

## 永続化と同時実行

データベースに置くものは、収集したデータ、リポジトリの一覧、GitHub トークン、収集ジョブ（識別子・状態・
進捗・結果）である。

- 同じ実体は 1 行だけ存在する。同じ収集を繰り返しても行は重複しない
- スキーマはバージョン管理され、適用済みかどうかを問い合わせられる。インスタンスの起動がスキーマを暗黙に
  書き換えることはない
- インスタンスが異常終了しても、コミット済みのデータは失われない
- 複数のインスタンスが同時に同じデータベースへ書き込んでも、データは壊れない
- 収集中でも、ほかの利用者は閲覧を続けられる
- ローカル開発もホストと同じデータベース製品を使う。開発とホストで保存層の実装を分けない

## 設定項目

変数名がすでに存在するものは実名で、ホスト化にあたって新設するものは役割で示す。新設分の変数名は設計時に決める。

| 設定 | 必須 | 無いときの振る舞い |
|---|---|---|
| データベース接続情報 | 必須 | 起動しない |
| 暗号鍵 | 必須 | 起動しない |
| 認証プロバイダの資格情報 | 必須 | 起動しない |
| セッション署名鍵 | 必須 | 起動しない |
| 許可 organization / 許可 login | いずれか必須 | 起動しない |
| `GITHUB_TOKEN` | 任意 | 画面から登録したトークンだけを使う |
| `GITHUB_API_URL` | 任意 | 公開 GitHub を使う |
| `ALLOW_TOKEN_UI` | 任意 | 許可する |
| `PORT` | 任意 | 3000 |

`DATA_DIR` は存在しない。インスタンスはデータ用のディレクトリを持たない。

## 受け入れ

上記のユースケースは自動テストで確認できる。保存層に対する読み書きは、実際のデータベースに対して実行する
テストで確認する。テストはコマンド 1 つで実行でき、CI で走る。

## 対象外

- 利用者ごとのデータ分離、組織をまたぐ相互不可視性
- メトリクスの定義・算出方法・チャートの変更
- GitHub からの収集ロジックそのものの作り直し
- 既存のローカルデータベースファイルからの移行
- 監査ログ、利用者ごとの操作履歴
